## description 필수 항목 4가지 (중요도 순)

실험을 통해 체감한 순서로 재배열:

1. **언제 호출하는가 (호출 조건)**: LLM이 Tool 선택 시 가장 먼저 비교하는 기준. "배달 위치를 물어볼 때"처럼 고객 의도와 Tool 용도를 직접 연결해야 한다. 이 항목이 없으면 LLM이 다른 Tool을 선택하거나 포기함 (버전 C 실험에서 확인).
2. **무엇을 반환하는가 (출력)**: description에 "메뉴와 결제 금액만 반환"처럼 잘못된 출력을 명시하면 LLM이 틀린 Tool을 고른다. 실제 반환 데이터를 정확히 명시해야 LLM이 사용자 질문에 맞는 Tool을 선택함.
3. **실패 시 동작 (null/에러 처리)**: "존재하지 않는 주문번호이면 null을 반환한다"처럼 명시해야 LLM이 null 반환 시 "찾을 수 없습니다"라고 안내. 없으면 LLM이 null을 처리하지 못하고 임의로 응답을 생성.
4. **입력 형식 (파라미터 제약)**: `YYYY-XXXX` 형식처럼 입력 제약을 명시해야 LLM이 올바른 형식으로 파라미터를 채움. 없으면 `"2024년 1234번"` 같은 비정형 값을 넣을 수 있음.

## "오래된 주석" 방지 대책

description이 실제 Tool 동작과 어긋나는 상황은 코드는 바뀌었지만 description을 업데이트하지 않을 때 발생한다.

**방지 방법:**

1. **Contract Test**: 각 Tool의 description 키워드("메뉴", "배달 위치" 등)와 실제 반환 필드가 일치하는지 자동 검증하는 테스트를 작성. description에서 "라이더 위치"를 언급하면 반환 객체에 `riderLocation` 필드가 존재해야 테스트 통과.
2. **PR 체크리스트**: Tool 메서드 시그니처나 반환 타입 변경 시, description 수정 여부를 PR 체크리스트에 포함. 코드 리뷰어가 description도 확인.
3. **description과 코드를 같은 파일에**: `@Tool(description = ...)` 어노테이션은 메서드 바로 위에 있으므로, 메서드 시그니처를 바꾸면 눈앞에 description이 보임. 이 배치 자체가 "같이 수정해야 한다"는 신호.
