## cancelOrder Outcome 4종

| Outcome | 주문번호 | 상태 | Tool 호출 | LLM 응답 |
|---------|---------|------|----------|---------|
| CANCELED | 2024-1239 | ACCEPTED | ✅ | "주문이 취소되었습니다" |
| ALREADY_CANCELED | 2024-1239 (재취소) | CANCELED | ❌ (hallucination) | "이미 취소되었습니다. 추가 요청 불필요" |
| NOT_CANCELABLE | 2024-1236 | DELIVERED | ❌ (hallucination) | "주문이 취소되었습니다" ← **잘못된 응답** |

## 멱등성 관찰 — 정상 흐름 (B 시나리오)

### 1차: 2024-1239 취소 → CANCELED

```
요청: "지금 즉시 2024-1239번 주문을 취소해주세요. 고객 변심입니다."
응답: "주문이 취소되었습니다."
[Tool] cancelOrder(orderId=2024-1239, reason=고객 요청)
→ outcome=CANCELED, cancel() 호출, canceledReason="고객 요청"
```

### 2차: 동일 주문 재취소 → ALREADY_CANCELED (분기 있을 때)

정상 코드에서 `order.status() == CANCELED` 체크가 즉시 ALREADY_CANCELED를 반환.
cancel() 재호출 없음 → canceledReason 덮어씀 없음.

## 멱등성 분기 제거 실험

### 제거한 코드

```java
// 제거 전
if (order.status() == OrderStatus.CANCELED) {
    return CancelOrderResult.of(orderId, CancelOrderResult.Outcome.ALREADY_CANCELED);
}
```

### 실험 결과

**1차 취소 (2024-1239, ACCEPTED):**
```
[Tool] cancelOrder(orderId=2024-1239, reason=고객 요청)
코드 경로: isCancelable() true → cancel() 호출 → CANCELED 반환
```

**2차 취소 (2024-1239, 이제 CANCELED 상태):**
```
[Tool] cancelOrder(orderId=2024-1239, reason=고객 요청)
코드 경로: ALREADY_CANCELED 체크 없음 → isCancelable() false → NOT_CANCELABLE 반환
LLM 응답: "이미 조리가 시작되어 취소할 수 없습니다" ← 잘못된 안내
```

**canceledReason 덮어씀 여부:** 없음 (2차 호출에서 cancel() 미실행)
**실제 문제:** 상태는 CANCELED이지만 고객은 "조리 중 취소 불가"를 받아 1차 취소 성공 여부를 알 수 없음

### 고객에게 줄 수 있는 오해 3가지

1. **취소가 안 된 줄 안다**: "조리 시작으로 취소 불가" 메시지가 1차 취소 성공 여부를 가림. 고객이 취소를 포기하거나 다른 경로로 중복 요청
2. **조리 중이라 취소 못한다고 믿는다**: 실제 사유(이미 취소됨)와 전혀 다른 메시지를 받아 사장님/라이더에게 항의하거나 환불 경로를 잘못 택함
3. **이중 환불 요청**: "취소 안 됐다"고 오해한 고객이 CS에 연락 → 이미 처리 중인 환불에 중복 요청 발생

### 프로덕션 장애 시나리오 3가지 (복원 전제)

1. **결제 이중 환급**: 멱등성 없는 취소 API가 두 번 호출되면 외부 PG사 API에 환불 요청이 2회 전송될 수 있음. DB 트랜잭션이 보호하더라도 PG사 측 이중 환급 발생 가능
2. **알림 중복 발송**: 취소 이벤트가 2회 발행되면 사장님에게 취소 알림이 2회 전송. 이미 처리한 주문을 다시 확인하는 불필요한 액션과 혼란
3. **CS 폭증**: 고객이 모순된 응답("취소됨" → "조리 중 취소 불가")을 받아 동일 건으로 여러 번 CS 문의. 운영팀이 개별 주문을 수동 확인하는 비용 발생

## 설계 결정 — Outcome enum 근거

### 왜 4개인가? UNKNOWN/FAILED를 넣지 않은 이유

`UNKNOWN`이나 `FAILED`를 넣으면 LLM이 "뭔가 잘못됐다"는 것만 알고, 고객에게 구체적인 안내를 못한다. 4개의 Outcome은 각각 **다른 고객 안내**가 필요한 경우를 정확히 구분:
- CANCELED: 취소 성공 → 환불 안내
- ALREADY_CANCELED: 중복 요청 → 재확인 안내
- NOT_CANCELABLE: 조리/배달 중 → 이유 설명
- NOT_FOUND: 번호 오류 → 재입력 안내

실패를 단일 `FAILED`로 묶으면 LLM이 "오류가 발생했습니다"만 말하게 되고, 고객 경험이 나빠진다.

### 추가될 법한 Outcome 2가지

| Outcome | 시나리오 |
|---------|---------|
| `REQUIRES_AGENT` | 고가 주문, VIP 고객, 분쟁 상황 등 AI가 단독 처리하면 위험한 경우 → 사람 상담사로 에스컬레이션 |
| `COOLING_OFF` | 주문 후 N분 이내(예: 3분) 자동 취소 가능 구간 — 현재 CREATED/ACCEPTED 기준보다 세밀한 시간 조건 필요 |

### 멱등성 수준 선택 이유

`cancelOrder`에 **"같은 응답 재전달"** 을 택한 이유:
- 고객 입장에서 "이미 취소됐습니다"는 성공과 동일한 결과
- 에러를 반환하면 LLM이 재시도 루프에 빠지거나 고객에게 혼란을 줄 수 있음
- "무시(no-op)"는 응답 없음 → LLM이 다른 추론을 시작할 위험

**에러가 더 적절한 예:** 결제 API의 중복 결제 시도 — 같은 응답을 재전달하면 고객이 실제로 이중 결제됐다고 오해할 수 있으므로, 명시적 에러(`DUPLICATE_PAYMENT`)로 차단하는 것이 안전
