## 설계 결정 문서

### Q1. `OrderDetailView`에서 의도적으로 뺀 필드는?

`deliveryAddress`, `riderLocation`, `canceledReason`을 제외했다.

- `deliveryAddress`: 고객 입장에서 자신의 주소는 이미 알고 있고, LLM 응답에 포함되면 불필요한 개인정보 노출
- `riderLocation`: 배달 상태 조회(`getDeliveryStatus`)의 전용 필드. 두 Tool에 중복 포함하면 Tool 경계가 흐려짐
- `canceledReason`: 취소 결과 조회는 `cancelOrder`의 반환값(`CancelOrderResult`)이 담당. 조회 View에 포함하면 책임이 분산됨

### Q2. `@Tool` description을 한국어로 쓴 이유는?

한국어로 작성했다. 기준은 **시스템 프롬프트와 언어 일관성** — `BaedalPrompt.SYSTEM_PROMPT`가 한국어이고, 모델(`qwen2.5`)이 한국어 컨텍스트에서 동작한다. description은 LLM이 읽는 API 문서이므로, 추론 언어와 일치시켜야 모델이 Tool 호출 조건을 정확히 판단할 수 있다.

### Q3. `OrderTools`를 하나의 클래스로 묶은 이유와 분리 기준

현재 수준에서는 Tool이 3개이고 모두 `OrderMockService` 하나에 의존하므로 하나로 충분하다. 분리한다면:
- **조회 vs 변경**: `OrderQueryTools`(getOrderDetail, getDeliveryStatus) / `OrderCommandTools`(cancelOrder) — CQRS 원칙 적용 시
- **도메인 경계**: 결제·환불 Tool이 추가되면 `PaymentTools`로 분리 — 의존하는 서비스가 달라지는 시점이 분리 기준
