# Round 3 — 3단계: JDBC 저장소 전환 실험 보고서

## 1. JDBC 전환 변경사항

### 1-A. 의존성 추가 (`build.gradle`)

```groovy
implementation 'org.springframework.ai:spring-ai-starter-model-chat-memory-repository-jdbc'
runtimeOnly    'com.h2database:h2'
```

### 1-B. Bean 충돌 방지 (`ChatMemoryConfig.java`)

```java
@Bean
@Profile("!jdbc")          // jdbc 프로필 활성 시 자동 구성된 JdbcChatMemoryRepository에 양보
public ChatMemoryRepository chatMemoryRepository() {
    return new InMemoryChatMemoryRepository();
}
```

**이유**: `spring-ai-starter-model-chat-memory-repository-jdbc`는 `JdbcChatMemoryRepository`를 자동 등록한다.
`@Profile("!jdbc")` 없이 두 Bean이 동시에 존재하면 `NoUniqueBeanDefinitionException`이 발생한다.

### 1-C. H2 스키마 파일 수동 생성

Spring AI 1.0.0 JDBC starter JAR에는 `schema-h2.sql`이 포함되어 있지 않다 (postgresql, sqlserver, mariadb, hsqldb만 제공).

해결책: 자동 구성이 기대하는 classpath 위치에 직접 생성.

**파일 위치**: `src/main/resources/org/springframework/ai/chat/memory/repository/jdbc/schema-h2.sql`

```sql
CREATE TABLE IF NOT EXISTS SPRING_AI_CHAT_MEMORY (
    conversation_id VARCHAR(36) NOT NULL,
    content TEXT NOT NULL,
    type VARCHAR(10) NOT NULL CHECK (type IN ('USER', 'ASSISTANT', 'SYSTEM', 'TOOL')),
    "timestamp" TIMESTAMP NOT NULL
);

CREATE INDEX IF NOT EXISTS SPRING_AI_CHAT_MEMORY_CONVERSATION_ID_TIMESTAMP_IDX
ON SPRING_AI_CHAT_MEMORY(conversation_id, "timestamp");
```

H2의 `MODE=PostgreSQL` 덕분에 PostgreSQL 문법(`"timestamp"` quoted identifier)을 그대로 사용한다.

### 1-D. `application-jdbc.yml` 핵심 설정

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:baedal;MODE=PostgreSQL;DB_CLOSE_DELAY=-1
    driver-class-name: org.h2.Driver
  ai:
    chat:
      memory:
        repository:
          jdbc:
            initialize-schema: embedded   # h2:mem → 자동 초기화
```

## 2. 시나리오 동작 확인 (1단계 5개 시나리오 재현)

`httpyac run round3_1.http --all` 로 jdbc 프로필 기동 앱에서 실행.

### 실행 로그 핵심 (exp-jdbc-mem.log 발췌)

| 시나리오 | 요청 | 결과 |
|---|---|---|
| S1 T1 | `2024-1234 어디쯤 있어요?` | getDeliveryStatus 호출, 상태 반환 |
| S1 T2 | `그거 언제 도착해요?` | "그거" → 2024-1234 해결, 도착 시각 반환 |
| S2 | `2024-1234 취소해주세요` (배달중) | 취소 불가 응답 |
| S3 T1 | `2024-1235 취소해주세요` (접수 완료) | 취소 처리 or 확인 요청 |
| S4 | `cust-B: 그 주문 어디쯤이에요?` | 컨텍스트 없어 주문번호 요청 |
| S5 | cust-C clear → `그거 언제 도착해요?` | clear 후 컨텍스트 없어 주문번호 요청 |

REST API로 JDBC 저장 확인:
```
GET /api/v1/session/ids        → ["cust-A","cust-B","cust-C"]
GET /api/v1/session/cust-A/messages → 8개 메시지 (USER/ASSISTANT 교대)
```

## 3. 재시작 실험

### 실험 절차

```
[실험 1] h2:mem — 재시작 시 데이터 소실
  1. jdbc 프로필로 앱 시작 (h2:mem)
  2. round3_1.http 시나리오 실행 → cust-A/B/C 세션 생성
  3. 앱 종료 (kill PID)
  4. 동일 설정으로 재시작
  5. GET /api/v1/session/ids 조회

[실험 2] h2:file — 재시작 후 데이터 영속
  1. application-jdbc.yml URL을 h2:file:./data/baedal로 변경
  2. initialize-schema: always로 변경 (h2:file은 embedded 판정 X)
  3. 앱 시작 → persist-test 세션에 대화 저장
  4. 앱 종료 → baedal.mv.db 파일 존재 확인
  5. 앱 재시작
  6. GET /api/v1/session/ids, persist-test/messages 조회
  7. 재시작 후 "아까 물어본 그 주문 취소해주세요" 요청
```

### 실험 결과

#### 실험 1: h2:mem 재시작

```
재시작 전: GET /api/v1/session/ids → ["cust-A","cust-B","cust-C"]
앱 종료
재시작 후: GET /api/v1/session/ids → []
           GET /api/v1/session/cust-A/messages → []
```

**→ h2:mem은 JVM 프로세스에 귀속. 재시작 시 데이터 전량 소실.**

#### 실험 2: h2:file 재시작

```
재시작 전: persist-test 세션에 6개 메시지 저장
           ls ./data/ → baedal.mv.db (28KB)
앱 종료
재시작 후:
  GET /api/v1/session/ids → ["persist-test"]
  GET /api/v1/session/persist-test/messages → 6개 메시지 완전 복원

재시작 후 대화 계속:
  요청: "아까 물어본 그 주문 취소해주세요"
  응답: "주문번호 2024-1234의 상태를 확인한 결과, 현재 배달 중이므로 취소할 수 없습니다."
```

**→ h2:file은 재시작 후에도 대화 컨텍스트 완전 유지. 지시 대명사 해결 포함.**

### h2:file 사용 시 주의사항

`initialize-schema: embedded` 설정은 Spring Boot의 `EmbeddedDatabaseType` 판정 기준을 따른다.
`jdbc:h2:mem:*` → embedded ✓, `jdbc:h2:file:*` → **NOT** embedded.
h2:file 사용 시 `initialize-schema: always` 또는 Flyway/Liquibase로 명시 관리해야 한다.

## 4. 저장소 비교 표

| 항목 | InMemoryChatMemoryRepository | JdbcChatMemoryRepository (h2:mem) | JdbcChatMemoryRepository (h2:file) | JdbcChatMemoryRepository (PostgreSQL) |
|---|---|---|---|---|
| **재시작 생존** | ✗ | ✗ | ✓ | ✓ |
| **멀티 인스턴스** | ✗ (JVM 내 공유) | ✗ | ✗ (파일 잠금) | ✓ |
| **감사 로그** | ✗ | ✗ (재시작 소실) | △ (파일 접근 필요) | ✓ (DB 쿼리 가능) |
| **개인정보 TTL** | 코드로만 제어 | - | 파일 삭제 | DELETE + 파티션 |
| **설정 복잡도** | 없음 | 스키마 파일 필요 | 스키마 + always 필요 | 별도 DB 인프라 |
| **적합한 환경** | 로컬 개발, 단위 테스트 | 통합 테스트, CI | 단일 서버 스테이징 | 프로덕션 |

## 5. 결정 트리 — 운영 조건 → 저장소 선택

```
재시작 후에도 대화 이력이 필요한가?
│
├─ NO → InMemoryChatMemoryRepository
│        (로컬 개발 / 테스트 / stateless 서비스)
│
└─ YES → JDBC가 필요
          │
          복수 서버 인스턴스(수평 확장)가 필요한가?
          │
          ├─ NO → JdbcChatMemoryRepository (h2:file)
          │        (단일 서버, 스테이징, 소규모 서비스)
          │        주의: initialize-schema: always 필요
          │
          └─ YES → JdbcChatMemoryRepository (PostgreSQL / MySQL)
                    (프로덕션, 마이크로서비스)
                    │
                    보존 기간 / 감사 / 개인정보 요구가 있는가?
                    ├─ NO → 기본 설정으로 충분
                    └─ YES → TTL 컬럼 + 삭제 배치 + 접근 로그 추가 설계
```

## 6. 설계 결정 질문

### Q1: InMemory로 충분한 상황 vs JDBC가 필요한 상황의 경계는?

순서대로 한계에 도달하는 시점:

1. **서버 재시작**: InMemory 첫 번째 한계. 배포 후 대화가 모두 끊긴다. h2:file로 해결 가능.
2. **멀티 인스턴스**: h2:file 한계. 로드밸런서 뒤에 서버 2대가 있으면 세션 분리. PostgreSQL 공유 DB 필요.
3. **감사/보존 기간**: 고객 문의 이력을 3년 보관해야 한다면 DB 쿼리로 조회 가능해야 한다.
4. **개인정보 삭제 요구**: GDPR/개인정보법상 탈퇴 고객 대화 삭제 → DELETE WHERE user_id 가능해야 한다.

### Q2: @Profile("!jdbc") 필요성

Spring AI 1.0.0 자동 구성은 `JdbcChatMemoryRepository`를 DataSource가 있으면 무조건 등록한다.
`@Profile("!jdbc")` 없이 `InMemoryChatMemoryRepository` Bean도 등록하면 `ChatMemoryRepository` 타입 Bean이 2개가 되어
`NoUniqueBeanDefinitionException`이 발생한다.

### Q3: initialize-schema 옵션별 동작

| 값 | 동작 |
|---|---|
| `embedded` | Spring Boot가 EmbeddedDatabaseType으로 판정한 DB만 초기화 (h2:mem ✓, h2:file ✗) |
| `always` | 항상 초기화 (`CREATE TABLE IF NOT EXISTS`이므로 멱등) |
| `never` | 초기화 안 함 (Flyway/Liquibase로 별도 관리) |
