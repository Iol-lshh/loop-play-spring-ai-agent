# Round 3 — 1단계: ChatMemory 3레이어 + X-Session-Id + 지시 대명사 시나리오

## 구현 요약

### ChatMemory 3레이어 (`ChatMemoryConfig.java`)

| 레이어 | 클래스 | 역할 |
|-------|--------|------|
| 저장소 | `InMemoryChatMemoryRepository` | 메시지 CRUD — JPA Repository에 대응 |
| 정책 | `MessageWindowChatMemory` (maxMessages=20) | 슬라이딩 윈도우로 최근 N개만 유지 |
| 어댑터 | `MessageChatMemoryAdvisor` (order=10) | ChatClient 호출 흐름에 Memory를 주입 |

```java
private static final int MAX_MESSAGES = 20;

@Bean ChatMemoryRepository chatMemoryRepository() { return new InMemoryChatMemoryRepository(); }

@Bean ChatMemory chatMemory(ChatMemoryRepository r) {
    return MessageWindowChatMemory.builder().chatMemoryRepository(r).maxMessages(MAX_MESSAGES).build();
}

@Bean MessageChatMemoryAdvisor messageChatMemoryAdvisor(ChatMemory m) {
    return MessageChatMemoryAdvisor.builder(m).order(10).build();
}
```

### 세션 운영 엔드포인트 (`SessionController.java`)

| HTTP | 경로 | 구현 |
|------|------|------|
| GET | `/api/v1/session/{id}/messages` | `chatMemory.get(sessionId)` → `MessageView` 리스트 |
| DELETE | `/api/v1/session/{id}` | `chatMemory.clear(sessionId)` |
| GET | `/api/v1/session/ids` | `chatMemoryRepository.findConversationIds()` |

### Controller Memory 연결

`AssistantController`와 `SupportController` 양쪽에 동일 패턴 적용:

```java
@RequestHeader(value = "X-Session-Id", defaultValue = "default") String sessionId

// ChatClient 조립 (AssistantChatClientConfig — 싱글톤 Bean)
.defaultAdvisors(memoryAdvisor, performanceAdvisor)  // memoryAdvisor가 첫 번째

// 요청 단위로 conversationId 주입
.advisors(a -> a.param(ChatMemory.CONVERSATION_ID, sessionId))
```

`ChatClient.Builder`를 요청마다 `.build()`하면 Tool/Advisor가 누적되어 "Multiple tools with the same name" 오류가 발생한다. `AssistantController`는 조립이 끝난 `ChatClient` Bean을 주입받아 사용한다.

## 설계 결정 문서

### Q1. MAX_MESSAGES=20을 선택한 근거

배달 상담의 평균 대화 흐름을 아래처럼 가정했다.

| 단계 | 예시 | 턴 |
|------|------|----|
| 주문 조회 | "2024-1234 어디쯤이에요?" + 응답 | 2 |
| 도착 시간 확인 | "그거 몇 분 남았어요?" + 응답 | 2 |
| 취소 요청 | "취소해주세요" → "이유?" → "단순 변심" + 응답 | 4 |
| 재주문 확인 | "다른 메뉴로 다시 주문하면 되나요?" + 응답 | 2 |

합계 약 10턴(USER+ASSISTANT=10개 메시지). 20을 선택하면 평균 상담 2회 분량을 커버하면서 토큰 비용도 무한 증가를 막을 수 있다.

- 너무 작으면(2~4): 시나리오 3처럼 이전 턴 참조가 실패한다.
- 너무 크면(Integer.MAX_VALUE): 장기 세션에서 입력 토큰이 선형 증가해 지연/비용이 증가한다.
- 20: USER/ASSISTANT 합산 10턴 분량 — 배달 상담 맥락을 충분히 유지하면서 토큰 상한을 제어한다.

### Q2. `defaultValue = "default"` 폴백의 구체적 위험 시나리오

| 시나리오 | 위험 |
|----------|------|
| 구버전 클라이언트 | X-Session-Id 헤더를 모르는 구 앱이 헤더 없이 요청하면, 모든 구버전 사용자의 대화가 `"default"` 세션 하나에 합산된다. A 고객의 주문번호가 B 고객 응답에 포함될 수 있다. |
| 어뷰저 의도 제거 | 헤더를 의도적으로 빼면 다른 "헤더 없는" 요청들의 대화 이력을 엿볼 수 있다. 특히 이전 사용자가 남긴 주문번호·민감 정보가 "default" Memory에 쌓여 있을 경우 개인정보 사고로 이어진다. |

프로덕션에서는 헤더 누락 시 **400 Bad Request**를 반환하거나, 서버에서 UUID를 발급해 응답 헤더로 내려주는 방식이 안전하다.

### Q3. 세션 식별 실무 대안 비교

| 방식 | 장점 | 단점 | 배달 상담 적용 |
|------|------|------|----------------|
| HTTP 헤더 (`X-Session-Id`) | 구현 단순, 비 브라우저 클라이언트 친화적 | 클라이언트가 직접 값을 결정 → 위조/충돌 가능 | 내부 API / 서버 간 호출에 적합 |
| 쿠키 | 브라우저가 자동 포함, 만료 설정 가능 | 모바일 앱에서 별도 처리 필요, CSRF 고려 | 웹 채팅 UI에 적합 |
| JWT 클레임 | 서명 검증으로 위조 방지, `sub` 클레임으로 고객 ID 추출 | 토큰 만료/갱신 로직 필요 | 로그인 고객 식별 시 최적 |
| URL 경로 (`/session/{id}/chat`) | RESTful, 캐시 친화적 | URL에 세션 ID 노출, 공유 링크 위험 | 지원 상담 티켓 URL로 활용 가능 |

### Q4. 클라이언트가 세션 ID를 직접 결정하는 방식의 보안 리스크

클라이언트가 임의의 `X-Session-Id`를 보낼 수 있으면:

- **세션 탈취**: 공격자가 다른 사용자의 세션 ID를 추측·열거해 해당 대화 이력을 읽거나 오염시킬 수 있다.
- **대화 오염**: 악의적 입력을 특정 세션 ID로 주입해 그 세션 사용자에게 잘못된 응답을 유도한다.

방어 방법:

| 방법 | 설명 |
|------|------|
| 서버 발급 UUID | 로그인 시 서버가 UUID를 생성·반환. 클라이언트는 발급받은 값만 사용 가능 |
| JWT 서명 검증 | 토큰의 `sub`(사용자 ID)를 서버에서 검증. 위조 불가 |
| 세션 소유권 확인 | 요청 세션 ID가 인증된 사용자 ID와 매핑되는지 서버에서 검증 |
