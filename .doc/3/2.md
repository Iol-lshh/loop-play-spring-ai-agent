# Round 3 — 2단계: Memory 크기 실험 + 실패 관찰

## 실험 개요

`MAX_MESSAGES`를 3가지 값으로 바꾸고 동일한 10턴 시나리오를 실행해 입력 토큰, 응답 시간, 지시 대명사 해결 성공률을 정량 비교한다.

**10턴 시나리오:**

| 턴 | 메시지 | 판정 대상 |
|----|--------|---------|
| T1 | "2024-1234 배달 상황 알려주세요" | — |
| T2 | "그거 몇 분 남았어요?" | ✓ "그거"=1234 |
| T3 | "2024-1235 주문도 있는데 메뉴 뭐였죠?" | — |
| T4 | "아 그 버거 세트" | ✓ 1235 메뉴 맥락 |
| T5 | "2024-1234 취소 가능해요?" | — |
| T6 | "그럼 1235는 취소되죠?" | — |
| T7 | "그거 취소해주세요" | ✓ "그거"=1235 |
| T8 | "아까 1234는 언제 도착해요?" | — |
| T9 | "그 주문 라이더 위치 다시 확인" | ✓ "그 주문"=1234 |
| T10 | "요약해 주세요 지금까지 제가 뭘 물어봤는지" | — |

| T4 | "아 그 버거 세트" | "「2024-1235」의 메뉴는 「버거 세트」였습니다." | ✅ 1235 해결 |

```
3. 「2024-1234」 주문의 도착 예정 시간은 23시 12분경입니다.
```

## 실험 B (MAX=2) — 실패 관찰

### 왜 MAX=2는 부족한가

`MessageWindowChatMemory(maxMessages=2)`는 최근 **메시지 2개**(USER 1건 + ASSISTANT 1건)만 유지한다.

```
T1 처리 후 Memory: [T1-USER, T1-ASSISTANT]  ← 2개 full
T2 처리 후 Memory: [T2-USER, T2-ASSISTANT]  ← T1 쌍 삭제
T3 처리 후 Memory: [T3-USER, T3-ASSISTANT]  ← T2 쌍 삭제
T4에서 T1의 "2024-1234" 맥락 = 소멸
T4에서 T3의 "2024-1235" 맥락만 남음
```

**결과**: T4 이후 2턴 전 맥락은 물리적으로 프롬프트에 포함되지 않는다.

### 지시 대명사 실패 캡처

**T9 실패 — "그 주문 라이더 위치 다시 확인"**

이 시점 Memory 상태 (`[T8-USER, T8-ASSISTANT]`):
```
T8-USER: "아까 1234는 언제 도착해요?"
T8-ASSISTANT: "그런지 모르겠습니다, 다시 한번 확인해보겠습니다. 주문번호 1234의 배달 상태를 알려주시겠어요?"
```

T9 응답:
```
라이더의 현재 위치를 다시 확인하겠습니다.

주문번호 1234의 배달 상태를 알려주시겠어요?
```

T8의 ASSISTANT가 이미 "주문번호 1234를 알려달라"고 요청했으므로, T9에서도 동일 패턴 반복. Memory에 T1(1234 배달 성공 응답)이 없으니 Tool 실행 근거가 없다.

**T3 붕괴 — 모델 언어 혼란**

Memory: `[T2-USER, T2-ASSISTANT]` (T1의 1234 맥락 소멸)

T3 응답:
```
그거指的是2024-1235号订单的详情，您能提供一下具体的订单号码吗？这样我可以帮您查询所订购的菜品。
请您确认一下订单号码。
```

컨텍스트가 부족해지자 모델이 한국어/중국어 혼용 응답을 생성했다. 맥락 단절이 언어 모드 혼란으로 이어진 사례.

### 입력 토큰 변화

```
T1: 2442  ← 시스템 프롬프트 + 툴 정의 + T1-USER + Tool 결과
T2: 1274  ← 슬라이딩 윈도우 2개 (T1-USER + T1-ASSISTANT)
T3: 1279  ← 슬라이딩 윈도우 2개 (T2-USER + T2-ASSISTANT) ← T1 소멸
T4: 1239  ← 슬라이딩 윈도우 2개 (T3-USER + T3-ASSISTANT)
...
T10: 1225 ← 슬라이딩 윈도우 2개 (T9-USER + T9-ASSISTANT)
```

T3부터 토큰이 1220~1280 사이에 **고정**된다. 대화가 길어져도 입력 토큰은 증가하지 않는다 — 그게 바로 맥락 손실의 증거다.

## 실험 C (MAX=∞) — 입력 토큰 선형 증가 관찰

### 입력 토큰 선형 증가

```
T1: 2435  (기저: 시스템 + 툴 + T1-USER + Tool 결과)
T2: 1267  (T2부터 컨텍스트 누적 시작)
T3: 1363  (+96)
T4: 1470  (+107)
T5: 1526  (+56)
T6: 1613  (+87)
T7: 1701  (+88)
T8: 1810  (+109)
T9: 1885  (+75)
T10: 2000  (+115)
```

T3→T10: 1363 → 2000 = **+637 토큰**, 7턴 평균 **+91 토큰/턴**. 선형 증가 확인.

실험 A(MAX=20)의 T8~T10 평균(~1951)과 C의 T8~T10 평균(~1898)이 비슷한 것은 10턴에서 슬라이딩 윈도우 20이 아직 포화되지 않았기 때문이다. 대화가 21턴 이상으로 길어지면 A와 C가 분기된다.

### 지시 대명사 결과

| 턴 | 응답 | 판정 |
|----|------|------|
| T2 | "예상 배달 완료 시각은 오후 11시 21분입니다." | ✅ 1234 해결 |
| T4 | "2024-1234 주문의 메뉴는 버거 세트였습니다." | ⚠️ 1234로 오해 (1235 맥락 혼용) |
| T7 | "주문번호 2024-1234의 주문 취소를 요청하셨습니다." | ❌ **1235 대신 1234로 잘못 해결** |
| T9 | "라이더는 현재 역삼역 사거리 부근에서 배달 중입니다." | ✅ 1234 해결 |

T7에서 "그거"가 2024-1235가 아닌 2024-1234로 잘못 해결됐다. 원인: T6에서 AI가 "2024-1235 정보를 찾을 수 없다. 2024-1234 취소 이유를 알려달라"고 답했고, 전체 맥락(무제한 보존)에서 AI가 취소 논의의 최근 주체를 1234로 오인했다.

무제한 Memory는 "맥락이 많을수록 더 혼란할 수 있다"는 역설적 결과를 보여준다.

## 설계 결정 문서

### Q1. 슬라이딩 윈도우 vs 요약(Summarization) 전략

| 기준 | 슬라이딩 윈도우 (`MessageWindowChatMemory`) | 요약 전략 |
|------|------------------------------------------|---------|
| 작동 방식 | 최근 N개 메시지만 유지, 오래된 것 삭제 | 오래된 대화를 LLM이 요약해 압축 보존 |
| 토큰 비용 | N에 비례, 예측 가능 | 요약 호출 비용 추가 (1~2 LLM 왕복) |
| 정확도 | 오래된 맥락 완전 손실 | 오래된 맥락이 요약 형태로 보존 |
| 구현 복잡도 | 낮음 | 높음 (요약 시점·품질·프롬프트 관리 필요) |
| 적합 시나리오 | 짧은 세션 (배달 상담 1회 = 5~10턴) | 장기 세션 (법률 상담, 고객 이력 조회 등) |

**배달 상담에 슬라이딩 윈도우가 맞는 이유:**
- 배달 상담 평균 세션은 5~10턴으로 짧다.
- 주문번호가 명시되는 경우가 대부분이라 오래된 맥락 참조 필요성이 낮다.
- 요약 호출 추가 비용이 짧은 세션에서 오버헤드가 된다.

**요약 전략이 맞는 시나리오:**
- 고객이 어제 주문 건, 3주 전 환불 건을 함께 문의하는 장기 CS 상담
- 법률·의료처럼 이전 상담 전체 이력이 판단 근거가 되는 도메인

### Q2. "지시 대명사 해결 성공률" 프로덕션 기준

**기준: 10회 중 9회 이상 (90%)에서 프로덕션 허용**

근거:
- 배달 상담은 금전 거래와 직결된다. T7처럼 "그거 취소해주세요"가 틀린 주문번호로 해결되면 실제 취소 사고로 이어진다.
- 90% 미만이면 10명 중 1명꼴로 맥락 오해 → Tool이 틀린 orderId로 호출 → 엉뚱한 주문 취소 위험.
- 실험 결과: A(4/4=100%) ✅, B(1/4=25%) ❌, C(3/4=75%) ❌
- 따라서 MAX=2와 MAX=∞는 프로덕션 부적합.

### Q3. 배달 상담에서 "오래된 대화"가 의미 있는 경우

| 케이스 | 설명 | Memory 요구사항 |
|--------|------|-----------------|
| 3시간 전 주문 재문의 | "아까 1234 시킨 거 아직도 안 왔어요" — 3시간 전 대화 필요 | 세션 수명 연장 필요 (InMemory 불가, JDBC 필요) |
| 어제 환불 건 재문의 | "어제 환불 신청했는데 처리됐나요?" | 세션 간 영속성 필요 (고객 단위 DB 저장) |
| 재주문 패턴 참조 | "저번에 주문한 것과 같이 해주세요" | 고객 단위 장기 Memory 필요 |

이 케이스들은 현재 InMemory + 세션 단위 구현으로는 처리 불가하다. 3단계에서 JDBC 저장소로 전환하면 세션 간 영속성이 생기지만, 고객 단위 장기 Memory는 별도 설계가 필요하다.

### Q4. Memory를 세션이 아닌 고객 단위로 영속 유지한다면

**가능해지는 기능:**
- 단골 고객 패턴 인식 ("자주 주문하시는 교촌치킨 강남점이군요")
- 과거 환불·취소 이력 조회 없이 AI가 이력 참조
- 재주문 시 "저번과 같이"로 처리 가능

**새로운 리스크:**
| 리스크 | 설명 |
|--------|------|
| 개인정보 무제한 누적 | 주문 이력, 주소, 민감 패턴이 영구 저장 → GDPR/개인정보보호법 위반 위험 |
| 세션 간 오염 | 과거 대화 맥락이 현재 주문에 혼입 → 틀린 주문번호 참조 |
| 저장소 비용 | 고객 수 × 대화 수 × 메시지 크기 — 수십 GB 급 스토리지 |
| 보존 기간 정책 | "얼마나 오래 보관하나?" — 법적 의무 + 기술 설계 필요 |
