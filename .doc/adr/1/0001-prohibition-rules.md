# ADR 0001: System Prompt 금지 규칙 3가지 선택

## 맥락
배달 고객 상담 AI는 LLM이 자유롭게 응답을 생성한다. 제약 없이 두면 아래와 같은 문제가 발생한다.

- 환불·보상 여부를 LLM이 임의로 약속 → 실제 처리 불가 시 고객 불만 및 법적 책임
- 라이더/업주 개인정보를 응답에 포함 → 개인정보보호법 위반
- 타사 서비스와 비교하는 발언 → 브랜드 리스크 및 사실과 다른 정보 제공 가능성

이 세 가지는 CS 현장에서 실제로 분쟁·사고로 이어질 수 있는 고위험 영역이다.

## 결정

### 금지 규칙 1: 권한 제한 (환불·보상·쿠폰 약속 금지)
환불 가능 여부, 보상 금액, 쿠폰 지급은 내부 정책과 담당자 판단이 필요하다.
LLM이 "환불해드리겠습니다"라고 답변하면 고객은 이를 확약으로 받아들이지만, 실제 처리 단계에서 거절될 경우 2차 불만이 발생한다.
→ 항상 "정책 확인이 필요합니다"로 응대하고, CHECK_MANUAL 또는 ESCALATE로 분기한다.

### 금지 규칙 2: 보안/중립 (개인정보 노출 금지, 타사 비교 금지)
라이더 이름·연락처, 업주 정보는 개인정보로 고객에게 제공할 수 없다.
타사(쿠팡이츠, 요기요 등) 비교는 사실 여부와 관계없이 브랜드 리스크를 초래한다.
→ 두 사안의 성격(개인정보 / 중립성)이 다르지만, "시스템 바깥의 정보를 노출하지 않는다"는 공통 원칙으로 묶어 하나의 규칙으로 선언한다.

### 금지 규칙 3: 근거 기반 (추측·단정 금지)
LLM은 정보가 부족해도 자연스러운 문장을 생성하려는 경향이 있다.
배달 위치, 도착 시각, 환불 금액 등은 실시간 데이터 없이 단정하면 오정보가 된다.
→ 정보 부족 시 추측 대신 반드시 NextAction(ASK_FOR_INFO, CHECK_MANUAL 등)으로 분기한다.

## 결과
- LLM이 책임 범위 밖의 약속을 하지 않아 CS 사고 리스크가 줄어든다.
- 금지 규칙이 명시적이므로 프롬프트 변경 시 의도하지 않은 규칙 제거를 방지할 수 있다.
- 규칙이 3개로 압축되어 있어 프롬프트 토큰 비용 대비 효과가 높다.
